# NEXUS Baseline Benchmark Methodology

## Scope

The CI benchmark is an engineering smoke test for encoded size and per-operation timing. It is not a publication-quality performance study and does not establish that NARF is faster or smaller than established codecs.

## Workloads

The current harness uses five deterministic synthetic inputs, each 16 KiB:

- A constant byte repeated throughout.
- A four-byte periodic sequence.
- An 8-bit ascending ramp.
- Repeated English-like text bytes from a fixed alphabet.
- A deterministic xorshift-generated byte sequence.

These workloads are useful for reproducibility and exercising contrasting structure, but they are not representative substitutes for public compression corpora or real application data.

## Compared representations and size accounting

Every reported `encoded_bytes` value is the complete byte sequence produced by the corresponding benchmark encoder:

- **Identity:** the original bytes unchanged; no wrapper is added. This is a raw-data lower-bound baseline when the caller already knows the input length.
- **Pair RLE:** an 8-byte frame header (`PRL1` magic plus a 32-bit big-endian original length), followed by pairs of non-zero run count and byte value. A run is split into chunks of at most 255 bytes.
- **NARF v3:** the full 17-byte NARF header plus raw or token-coded body.
- **LZ4:** the `lz4_flex` size-prepended representation, including its 4-byte uncompressed-length prefix.
- **Zstandard:** the complete Zstandard frame emitted at compression level 3.
- **Brotli:** the complete Brotli stream emitted with quality 5 and a 4 KiB writer buffer.

The ratio is `encoded_bytes / input_bytes`. Codec settings and framing are part of the comparison. Pair RLE is a deliberately simple benchmark baseline, not a proposed production format.

## Timing

Each dataset/codec/operation pair receives five warm-up calls followed by 30 individually timed calls. Encode and decode are timed separately. Samples are reported as nanoseconds per original input byte.

Percentiles use the nearest-rank definition. With 30 samples, p99 is the maximum observed sample; it should not be interpreted as a stable tail-latency estimate. The benchmark reports p50, p95, and p99 to make the sample distribution visible, not to imply statistical confidence.

The CI artifact contains a strict CSV file plus a separate metadata text file with Rust and Cargo versions, runner OS and architecture, kernel string, and CPU model when available. The benchmark executable does not mix metadata comments into the CSV.

## Limitations and interpretation

- CI currently runs the benchmark on one Linux hosted runner. Results from different runner instances may use different hardware.
- The workloads are synthetic and fixed at 16 KiB.
- The harness does not yet report peak resident memory, CPU cycles, energy, p99 confidence intervals, or streaming behavior.
- Thirty samples are adequate for a first comparison but insufficient for strong tail-latency claims.
- Public corpora such as Canterbury, Silesia, Calgary, and appropriately licensed enwik8 samples remain future work. Dataset versions, checksums, licenses, and preprocessing must be recorded before those results are published.
- A single successful CI run is not an independent replication. Performance conclusions require multiple runs on documented, comparable hardware and raw artifact review.

Do not infer security, novelty, standards compliance, or production readiness from these measurements.
