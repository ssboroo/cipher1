# NARF Baseline Benchmark

## Purpose

This benchmark compares the NEXUS Adaptive Residual Transform (NARF) with LZ4, Zstandard, Brotli, identity, and a deliberately simple pair-RLE reference across five deterministic synthetic workloads.

It is an engineering smoke test, not evidence that NARF is competitive with established compressors. Codec libraries are benchmark-only development dependencies and are not part of the runtime crate dependency graph.

## Run

From the repository root:

```bash
cargo bench -p nexus-transform --bench narf_baseline
```

The executable writes CSV to standard output with one row per dataset and codec. Columns include:

- `dataset`, `codec`, `input_bytes`, `encoded_bytes`, and `total_ratio`.
- Encode and decode p50, p95, and p99 nanoseconds per input byte.

All encoded sizes include the complete representation emitted by the benchmark implementation:

- Identity is the original bytes unchanged; no wrapper is added.
- Pair-RLE includes its complete 8-byte frame header (4-byte magic and 4-byte original length) plus its count/value payload pairs.
- NARF v3 includes its complete 17-byte frame header and raw or token-coded body.
- LZ4 uses the size-prepended representation, including its 4-byte uncompressed-length prefix.
- Zstandard reports the complete frame emitted at compression level 3.
- Brotli reports the complete stream emitted at quality 5 with a 4 KiB writer buffer and a 22-bit window.

## Synthetic workloads

- Repeated byte: a single repeated value.
- Periodic: a four-byte repeating pattern.
- Ramp: byte values cycling from 0 through 255.
- Text-like: a deterministic repeated English-character sequence.
- Deterministic random: xorshift32-generated bytes with a fixed seed.

Each workload is 16 KiB. The harness performs five warm-up calls and 30 individually timed calls per dataset, codec, and operation. It reports nearest-rank p50/p95/p99. With 30 samples, p99 is the maximum observed sample and is descriptive only, not a stable tail-latency estimate. The harness verifies deterministic encoding and round-trip decoding before timing.

## Interpretation rules

1. Treat these synthetic workloads as smoke tests, not representative public corpora.
2. Never compare timing numbers across different machines as if they were controlled experiments.
3. Run at least five independent process invocations on otherwise idle, documented hardware before publishing timing summaries.
4. Record CPU model, operating system, Rust/Cargo versions, target triple, build flags, codec versions/settings, and commit SHA.
5. Include complete framing and metadata in every encoded-size comparison.
6. Keep raw CSV output and run metadata with the experiment record.
7. Do not infer security, novelty, standards compliance, or production readiness from these measurements.

## Public-corpus follow-up

The current executable does not yet load public corpora. Before reporting public-corpus results, follow [PUBLIC_CORPUS_BENCHMARK_PROTOCOL.md](PUBLIC_CORPUS_BENCHMARK_PROTOCOL.md), including per-file license review, immutable version pinning, SHA-256 manifests, checksum verification, per-file results, and aggregate ratio calculation as total encoded bytes divided by total input bytes.

## Current limitations

The harness does not yet measure peak resident memory, energy, streaming latency, or confidence intervals. Its five synthetic inputs are fixed at 16 KiB. Thirty timing samples per operation are screening data only. Multiple independent runs and representative, legally usable public corpora are required before making broader compression or performance claims.
